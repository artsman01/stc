# СТК — вёрстка

Вёрстка сайта СТК на **Bootstrap 5 + SCSS**, без фреймворков и сборщиков поверх этого. Схема взята из проекта Domarti (`~/Desktop/Domarti`), который заказчика устраивал: плоские HTML-страницы в корне, один SCSS-файл на компонент, один `main.js`.

Этот файл — общая память проекта: по нему можно быстро войти в курс дела человеку и Claude. Если что-то в проекте меняется (цвета, размеры, брейкпоинты, новые иконки), правьте и здесь.

## Быстрый старт

```bash
npm install          # один раз
npm run watch:css    # пересобирает css/style.css при каждом изменении scss
npm start            # локальный сервер на http://localhost:5500
npm run build:css    # разовая сборка (для деплоя)
```

`css/style.css` — результат сборки, руками его не правим. Редактируем только `scss/`.

## Что где лежит

```
index.html            главная страница (пока пустой каркас)
css/style.css         собранный CSS (генерируется)
js/main.js            все скрипты сайта
scss/
  main.scss           точка входа, порядок подключения важен (см. ниже)
  _variables.scss     цвета из макета + переопределения переменных Bootstrap
  _tokens.scss        цвета как CSS-переменные --color-*
  _typography.scss    шкала шрифтов (desktop + mobile) и текстовые классы
  components/         по одному файлу на компонент (_icons, _icon-btn, _header, _hero, …)
assets/
  icons/              иконки: sprite.svg + отдельные .svg
  hero/               фото и паттерн первого экрана
  cta/                фон и паттерн CTA-блока
  catalog/, industries/  фото карточек каталога и отраслей
  vendor/swiper/      собранный Swiper (копия из node_modules, см. раздел про Swiper)
  logo.svg            знак СТК (белый), logo-text.svg — надпись «Современные технологии контроля»
```

Порядок в `main.scss` (менять нельзя): `variables` → `bootstrap` → `tokens` → `typography` → `components/*`. Переменные должны идти до Bootstrap, чтобы он их подхватил; компоненты после, чтобы перебивать его стили.

### Типографика

Шрифт — **Wix Madefor Display** (подключается с Google Fonts в `<head>`, веса 400/500/600/700, кириллица есть). Межбуквенный интервал везде 0.

Заголовки (вес 700). **На мобильной версии они меньше**, шаги стали мельче:

| Стиль | Desktop, размер / межстрочный | Mobile, размер / межстрочный |
|---|---|---|
| display | 48 / 56 | 28 / 36 |
| h1 | 40 / 48 | 24 / 32 |
| h2 | 28 / 36 | 22 / 28 |
| h3 | 24 / 32 | 20 / 26 |
| h4 | 18 / 28 | 16 / 22 |
| h5 | 16 / 24 | 14 / 20 |
| h6 | 14 / 22 | 12 / 20 |

Основной текст **одинаковый на desktop и mobile**:

| Стиль | Размер / межстрочный | Веса |
|---|---|---|
| lead | 16 / 24 | regular 400, medium 500, bold 600 |
| text | 14 / 20 | regular 400, medium 500, bold 600 |
| meta | 12 / 18 | regular 400, medium 500, bold 600 |
| caption | 10 / 16 | regular 400, medium 500, bold 600 |

Как это устроено в коде (`scss/_typography.scss`):

- Все размеры лежат в CSS-переменных `--h1-size`, `--h1-lh`, `--lead-size` и т. д. Мобильная шкала — это подмена этих переменных внутри media query, сами селекторы не повторяются.
- `h1`–`h6` и `.h1`–`.h6` берут размер из этих переменных. Для остальных стилей есть классы `.text-display`, `.text-lead`, `.text-meta`, `.text-caption`. Обычный `text` (14/20) — это базовый размер `body`, отдельный класс не нужен.
- Вес задаём утилитами Bootstrap: `.fw-normal` (400), `.fw-medium` (500), `.fw-semibold` (600, это «bold» у body-стилей в макете).
- Автомасштабирование заголовков Bootstrap (RFS) выключено, потому что размеры заданы макетом.

Мобильная шкала (`$type-mobile`) включается **ниже 768px**. Планшетный макет (768px) ещё использует desktop-размеры: на нём display остаётся 48/56.

## Брейкпоинты

В Figma три макета главной, от них и берём три раскладки. Границы совпадают со стандартными брейкпоинтами Bootstrap, поэтому `$grid-breakpoints` не менялся.

| Раскладка | Ширина | Макет в Figma | Bootstrap |
|---|---|---|---|
| mobile | до 767px | 393 | `< md` |
| tablet | 768–1199px | 768 | `md` … `< xl` |
| desktop | от 1200px | 1600 | `xl` и выше |

Что меняется на границах:

- **до `md`** — мобильная шкала заголовков, боковые отступы 16px (на tablet и desktop 48px), hero ниже (624px вместо 800px), в шапке нет телефона.
- **от `md`** — появляется телефон в шапке, крупнее логотип, отступы 48px.
- **от `xl`** — шапка становится полной: «Каталог» и меню «Компания / База знаний / Контакты» вместо бургера, а на hero подставляется другое, более крупное фото.

Макет фиксирован только на трёх ширинах, между ними всё тянется по ширине. Общего контейнера с центрированием у главной нет: контент прижат влево с отступами 48px. Если понадобятся другие границы (например, отдельный шаг для 1600+), их нужно добавить здесь и в `_variables.scss`.

## Первый экран (hero + шапка)

Файлы: `index.html`, `scss/components/_hero.scss`, `_header.scss`, `_icon-btn.scss`.

- Шапка лежит **поверх** hero (`.header--overlay`, `position: absolute`) и прозрачная: белый текст, белый логотип, тёмные круглые кнопки. Нижняя граница и подложка фото сделаны токенами `--color-border-on-img` и `--color-surface-default`.
- **При наведении на шапку** (и когда на элементе внутри неё фокус с клавиатуры) она плавно (0.2s) становится белой, как в макете: фон `--color-bg-primary`, граница `--color-border-light`, текст `--color-text-primary`, логотип `--color-brand-primary`, кнопки на `--color-bg-secondary`, счётчик на `--color-brand-secondary`. Обычная `.header` без `--overlay` всегда в этом «белом» виде.
- Цвета шапки лежат в CSS-переменных `--header-*`, `--icon-btn-*`, `--badge-*`: два вида отличаются только их значениями (миксин `header-solid` в `_header.scss`). Ховер включается только на устройствах с мышью (`@media (hover: hover)`), чтобы на телефоне после тапа шапка не залипала белой.
- Логотип (знак и надпись) нарисован через `mask`, а не `<img>`, поэтому его цвет меняется вместе с шапкой из одного SVG.
- Что видно в шапке, решают классы Bootstrap в разметке: `d-none d-xl-flex` (каталог и меню), `d-none d-md-flex` (телефон), `d-xl-none` (бургер).
- Фото фона: `<picture>` с двумя файлами. От 1200px `hero-desktop.jpg` (2400×1200, крупный план), иначе `hero-compact.jpg` (1152×1470, вертикальная обрезка, сделана под mobile). Оба `object-fit: cover`, прижаты к низу (`object-position: 50% 100%`), чтобы пол оставался в кадре.
- Диагональные линии (`assets/hero/pattern.svg`, белый 4%) один тайл 1600×800 прижат к низу по центру, рисуется поверх фото через `.hero::after`.
- Текстовый блок по центру по вертикали. Заголовок `h1.text-display`, ширина до 752px, подзаголовок `text-lead` до 476px.
- Высота hero: 800px на tablet и desktop, 624px на mobile (`min-height`).

## Спейсеры между секциями

Файл: `scss/components/_spacer.scss`.

Между секциями на главной в макете стоят инстансы `Spacer` — просто вертикальный отступ, 16px на mobile и 32px от tablet и выше (класс `.spacer`, брейкпоинт `md`, как у остальных размеров хедера).

Спейсер сразу после hero — особый, в Figma он называется «Overlap». Его фон совпадает с секцией **над** ним (тёмный hero), а внутри лежит белый блок высотой во весь спейсер со скруглёнными **верхними** углами (16px, фиксированно на всех трёх ширинах). Так как этот блок закрывает всю полосу кроме двух угловых скруглений, создаётся ощущение, что следующая (белая) секция наезжает на hero и её верх скруглён, а не просто идёт вертикальный отступ. Модификатор `.spacer--overlap` + элемент `.spacer__cap`:

```html
<div class="spacer spacer--overlap">
  <div class="spacer__cap"></div>
</div>
```

Спейсер между каталогом и CTA — уже обычный `.spacer` (`Default`, без своего фона). Дальше по странице (CTA → отрасли → решения → …) спейсеры ещё не сверстаны — когда дойдём до них, нужно каждый раз проверять в Figma, какой у них шаблон (`Default` или `Overlap`), это не подписано текстом, только визуально.

## Каталог на главной (HomeCatalog)

Файлы: `scss/components/_home-catalog.scss`, `_category-card.scss`, `_tabs.scss`; секция вставлена в `index.html` сразу после спейсера.

- Заголовок «Каталог оборудования» — это `<h1>` (наш токен h1 40/48 desktop, 24/32 mobile — совпал с макетом без единой новой переменной). Заголовки групп («Неразрушающий контроль» и т. д.) — `<h2>`, подписи карточек — `.text-lead.fw-semibold` (16/24), описание справа от заголовка — `.text-lead.text-body-tertiary` (16/24, цвет `text-muted`), подзаголовки групп — обычный текст с `.text-body-secondary`. Всё уже было в дизайн-системе, отдельные размеры не заводили.
- **Раскладка шапки секции** (заголовок / описание / табы) меняется на `xl`: до `xl` всё стоит в столбик в таком порядке — заголовок, описание, табы; от `xl` заголовок и табы образуют левую колонку, а описание становится правой колонкой (396px). Сделано через `grid-template-areas` с двумя наборами.
- **Отступы и зазоры** у этой секции не совпадают с отступами `.spacer` (16/32): здесь это 24px (mobile) / 32px (tablet, desktop) между крупными блоками и 16px (mobile) / 24px (tablet, desktop) внутри шапки. Цифры сняты прямо с макета и не сведены к общему токену — они встречаются только тут.
- **Сетка карточек** (`.category-grid`) — 1 колонка до `md`, 2 `md`–`xl`, 3 `xl`–`xxl` (1200–1399px — в macете такого шага нет, 4 карточки там смотрелись тесно), 4 от `xxl` (1400px). Зазор 8px. Карточка (`.category-card`) квадратная (`aspect-ratio: 1/1`), поэтому её размер просто следует из ширины колонки — отдельные px для 370/332/361 не понадобились.
- **Ховер карточки.** В Figma кнопка «Перейти» нарисована статично только на одной карточке в каждой группе — так в макете показан ховер-стейт, а не отдельный вид карточки. Поэтому кнопка есть у всех 18 карточек, но по умолчанию скрыта (`opacity: 0`) и появляется по `:hover`/`:focus-within`. Фото при этом слегка увеличивается (`scale(1.06)`) — блюр, который был здесь раньше (Figma даёт `backdrop-blur` с конкретным значением на карточке-примере), убрали по просьбе заказчика.
- Ховер, как и у шапки, работает только там, где есть настоящий указатель (`@media (hover: hover)`), плюс отдельно `:focus-within` — чтобы кнопка была доступна и с клавиатуры.
- Цвет подписи карточки в макете — `#1a1d21`, это не значение ни одного токена (ближайший — `--color-text-heading` `#1e222c`, отличие на 1 юнit по каналам). Взял токен, а не завёл отдельный цвет ради разницы, неразличимой глазом.
- Фотографии карточек (18 штук, `assets/catalog/*.jpg`) выгружены из Figma (1024×1024, конвертированы в JPEG). Названия файлов — английская транслитерация названия категории (`radiographic-control.jpg` и т. п.).
- **Табы фильтруют карточки** (см. «Фильтр каталога по табам» ниже) — не ссылки и не якоря, обычные `<button>`.
- Все карточки и кнопка «Перейти в каталог» на hero ведут на `catalog.html`, которого пока нет в проекте — появится, когда дойдём до каталога как отдельной страницы.

## Фильтр каталога по табам

Клик по табу показывает только карточки своей группы и прячет остальные — не прокрутка к ним, не подсветка, а реальный показ/скрытие. Код — отдельная IIFE в `js/main.js`.

- Каждая группа (разделитель + заголовок + сетка карточек) обёрнута в один `<div class="home-catalog__group" data-category="…">` — специально, чтобы прятать/показывать её одним `hidden`, а не тремя отдельными соседними элементами по отдельности. В `_home-catalog.scss` у этой обёртки тот же `gap`, что раньше был у `.home-catalog` между этими тремя элементами напрямую — оборачивание на вложенность зазоров не повлияло.
- Таб «Все» — `data-category="all"`, остальные — `data-category`, совпадающий с `data-category` своей группы (те же слаги, что раньше были `id` для якорей: `nondestructive-testing` и т. д.). Клик снимает активный класс со всех табов, ставит на нажатый, и показывает все группы либо только одну — по совпадению `data-category`.
- Мы **пробовали** делать табы прилипающими к шапке (`position: sticky`) и якорной прокруткой к группе — заказчик попросил откатить оба: и sticky-поведение (табы снова в обычном потоке, где и были), и переходы по ссылке (при них шапка перекрывала заголовок группы). Текущий фильтр не скроллит страницу вообще — просто меняет, что видно в том же месте.

## Sticky-шапка, отступ под якоря, зум на мобилке

Три небольших доработки поверх hero и HomeCatalog.

- **Шапка после скролла.** `.header--overlay` лежит поверх hero и позиционирована `absolute` внутри него — при обычной прокрутке она уехала бы вместе с hero и на всей остальной странице не осталось бы шапки вообще. `js/main.js` при `scrollY > 4` добавляет класс `.header--stuck`: `position: fixed` + тот же «белый» вид, что и при ховере (`header-solid`). Переключение происходит ровно там, где шапка и так стоит в верхней точке экрана, поэтому прыжка не видно — плавно перекрашиваются только цвета (существующий transition). Скролл обратно наверх убирает класс.
- **Отступ под якоря.** Табы каталога сами больше никуда не скроллят (см. «Фильтр каталога по табам»), но на странице могут появиться другие якорные ссылки, а браузер и сам подскролливает к `#hash` из адресной строки — на этот случай `scroll-padding-top` на `html` держит контент на `--header-h` (высота шапки, общая переменная в `_header.scss`) плюс 16px воздуха, чтобы заголовок не оказывался вплотную к нижнему краю зафиксированной шапки. Прокрутка плавная (`scroll-behavior: smooth`, отключается людям с `prefers-reduced-motion`).
- **Зум на мобилке.** В `<meta name=viewport>` добавлены `maximum-scale=1.0, user-scalable=no` (как в Domarti) — блокирует и щипок, и двойной тап, и заодно тот самый авто-зум Safari при фокусе на поле мельче 16px (это его отдельное поведение, но именно `maximum-scale=1.0` его и гасит). Раньше здесь ещё был запасной вариант — поднимать `font-size` полей до 16px на мобильных, но это меняло размер текста в полях относительно макета, поэтому убрали: полям (`.input-field`, `.checkbox-field__text`) оставили дизайновые 14px/12px, зум блокирует только viewport meta.

## Обычный спейсер и CTA-форма

Между каталогом и CTA стоит обычный `.spacer` — без модификатора `--overlap`, без своего фона: в Figma такой спейсер вообще ничем не залит, поэтому под ним просто видно фон страницы (белый). Ничего писать для него не пришлось, базовый `.spacer` (16px mobile / 32px от tablet) это уже делает.

Файлы CTA: `scss/components/_cta.scss`, `_input.scss`, `_checkbox.scss`.

- **Desktop и tablet.** Белая карточка с формой лежит поверх фото на всю секцию (тот же приём, что у hero: фото + затемнение `--color-surface-default` + диагональный паттерн, только свой SVG). У карточки декоративные уголки по четырём углам (`.cta__corner`) — в Figma это тонкие двусторонние рамки 16×16px, отступ 24px от края.
- **Паттерн растянут на 100%/100%**, а не показан в исходном размере 1600×668 как у hero: высота карточки на реальной странице зависит от содержимого формы и на практике оказалась больше 668px (688px на десктопе), из-за чего паттерн фиксированного размера не доставал до нижнего края блока. Растяжение не идеально — при таком соотношении сторон линии чуть теряют пропорции, — но при непрозрачности 4% это незаметно, а сам паттерн гарантированно всегда упирается во все четыре края независимо от реальной высоты карточки.
- **Фон** — своя фотография заказчика (`assets/cta/cta-home-1-bg.jpg`), не из Figma. Дважды присылалась и обрабатывалась через `ffmpeg` (`eq=brightness=-0.08:contrast=1.05:saturation=0.9`, поверх ещё стоит CSS-тонировка `--color-surface-default`, как у hero) — второй раз в повышенном качестве (2400×1200).
- **Mobile — другая раскладка, а не та же самая в столбик.** Фото становится обычной плашкой сверху (`aspect-ratio: 393/294`), а форма — простой белой секцией под ней, без скругления, без плавающей карточки и без уголков. Это одна и та же разметка (фон, потом карточка), только у `.cta__bg`/`.cta__card` меняются `position`/`padding`/`border-radius` по брейкпоинту `md` — дублировать форму под два разных вида не пришлось.
- **Заголовок карточки** — `<h2 class="cta__title h1 m-0">`: по размеру это `h1` (совпадает с тем, что в Figma тут те же 40/48 → 24/32, что и у заголовка каталога), но по цвету — не `--color-text-heading`, а `--color-text-primary` (в макете он именно такой, отдельный класс `.cta__title` это переопределяет).
- **Ссылки внутри текста** (телефон, «Политика обработки персональных данных», «Согласие») в макете тёмные, не синие. Вместо точечных переопределений в `_variables.scss` добавлены `$link-color: $body-color` и `$link-hover-color: $primary` — как в Domarti. На уже собранные компоненты это не повлияло: везде, где ссылки уже есть (шапка, табы, карточки каталога), цвет и так был переопределён явно.
- Смена цвета ссылок на ховере плавная — общий `a { transition: color 0.15s ease; }` в `_tokens.scss` (у Bootstrap ссылки без transition по умолчанию), а не точечно для телефона и текста согласий. Остальным ссылкам (например, в шапке) не мешает: у них тот же transition уже был задан явно. Табы это не касается — они `<button>`, а не `<a>`.
- **Поля и чекбоксы** — переиспользуемые компоненты (`.input-field`, `.checkbox-field`), а не разметка только для этой формы: они пригодятся на будущих страницах с формами. Фокус-стейт (тонкая обводка `brand-primary`) в макете не показан, это уже наше решение, стандартная доступная замена дефолтному Bootstrap-фокусу.
- Чекбокс — обычный `<input type="checkbox">`, просто перекрашенный (`appearance: none` + фон), а не `<div>`-имитация: работает с клавиатуры и скринридерами. Галочка — существующая иконка `assets/icons/check.svg`, отдельно из Figma её не тащили.
- Первый чекбокс отмечен и обязателен (`checked required`) — так и в макете. Второй — необязательный, без `checked`. Поле телефона тоже обязательное (`required`) — в макете это не показано, но для формы заявки естественно.
- Форма ничего никуда не отправляет: `<form>` без `action`, нажатие на «Отправить заявку» просто перезагрузит страницу. Бэкенда и вообще какой-либо серверной логики в проекте пока нет.
- Ссылки на «Политику обработки персональных данных» и «Согласие» ведут на `#` — страницы политики в проекте ещё нет.

## Swiper и слайдеры («Отрасли», «Решения»)

После CTA — снова обычный `.spacer` (без модификатора), затем секция `.industries`; после неё ещё один `.spacer` и `.solutions`.

**Swiper.** Поставлен как в Domarti: `npm install swiper`, файлы сборки (`swiper-bundle.min.css`/`.js`) скопированы в `assets/vendor/swiper/` и подключены как обычные `<link>`/`<script>` — страницы статичные, без сборщика, npm-версия из `node_modules` в браузер не попадает. При обновлении Swiper пересобрать это вручную: `cp node_modules/swiper/swiper-bundle.min.{css,js} assets/vendor/swiper/`.

Оба слайдера — один и тот же паттерн, инициализация в `js/main.js` (две похожие функции, `initIndustries`/`initSolutions`, вторая ссылается на комментарий у первой, а не повторяет его):

- **Карточки ниже `xl`** фиксированной ширины по брейкпоинту (296 → 332), `slidesPerView` в Swiper — `"auto"`: он просто показывает, сколько влезает по факту и обрезает последнюю по ширине контейнера — то самое «подглядывание» следующей карточки из макета.
- **От `xl` карточки растягиваются**, а не остаются на фиксированных 370px: в JS для этого брейкпоинта отдельно задан `slidesPerView: 4` (через `breakpoints: { 1200: {...} }`) — тогда Swiper сам вычисляет ширину слайда из реальной ширины контейнера и выставляет её инлайн-стилем, своего `width` для `xl` в SCSS карточек больше нет. Это же чинит по себе один нюанс: при фиксированной ширине карточек и `slidesPerView:"auto"` даже 15px полосы прокрутки браузера иногда рушили ровно 4 карточки в ряд до 3 — с числовым `slidesPerView` такого не бывает, сетка всегда считается от реального размера контейнера. Верхнего предела по ширине контента при этом нет — на экране шире 1600px карточки просто растягиваются ещё больше (так попросил заказчик).
- **Стрелки существуют в разметке дважды.** В Figma они на desktop/tablet стоят в шапке секции рядом с описанием, а на mobile — отдельным блоком под слайдером, то есть физически в разных родителях, а не просто переставлены CSS. Раз одним элементом это не сделать, стрелки продублированы (`d-none d-md-flex` / `d-flex d-md-none`), с одинаковыми классами (`.industries__nav-prev`/`-next`, `.solutions__nav-prev`/`-next`). Swiper подключён к ним через **строку-селектор**, а не через ссылку на конкретный DOM-узел — тогда он сам находит и синхронизирует все подходящие элементы, из двух копий работает только та, что видна в данный момент, вторая скрыта `display:none` и вне доступности. Копия в шапке (desktop/tablet) прижата к правому краю строки (`margin-left: auto` только на этой копии).
- **Слайдеры не зациклены** (в отличие от `.material-slider` из Domarti) — так попросил заказчик: доскроллили до конца — стрелка «вперёд» и сам слайдер дальше не двигаются (Swiper сам гасит прокрутку и вешает `.swiper-button-disabled` на кнопку), то же в начале для стрелки «назад». `.slider-nav-btn.swiper-button-disabled` уже было готово под это состояние.
- Иконки стрелок — уже существующие `angle-left`/`angle-right` из общего спрайта, ничего нового из Figma не тащили.
- И у секционного `<hr>`-разделителя, и у разделителя внутри карточки явно стоит `opacity: 1` — Bootstrap даёт `<hr>` `opacity: 0.25` по умолчанию, без переопределения линия на светлом фоне еле видна (`.home-catalog__separator` та же история, у него это уже стояло).

**«Работаем в контексте отрасли»** (`_industries.scss`, `_industry-card.scss`). Светлая секция, карточки квадратные (`aspect-ratio: 1/1`, как у `.category-card`). Картинки-иллюстрации (8 штук, `assets/industries/*.png`) — прозрачные PNG, рисуются с `opacity: 48%`, как в макете; из Figma пришли в 1800×650, здесь уменьшены до 900×650 — вес папки упал с 2.8 до 1.2 МБ. Заголовок карточки цвета `#1a1d21` (в макете) нормализован до `--color-text-heading`, как и в `.category-card__title`. Ховера у карточки нет — пробовали лёгкий подъём (`translateY(-8px)` + тень), заказчик попросил оставить без этого.

**«Решения под ваши задачи»** (`_solutions.scss`, `_solution-card.scss`). Тёмная секция (`--color-bg-dark`) со скруглением `border-radius: 16px` **по всем четырём углам** — у неё нет `--overlap`-подложки как у спейсера после hero, скругление даёт тот же эффект «плавающей карточки» само по себе, за счёт того, что секция лежит на белом фоне страницы и её отступов сверху/снизу (обычные `.spacer` до и после) достаточно, чтобы углы читались. Заголовок и описание белые (`.text-white`, `--color-text-on-img`, как у hero), секционный разделитель — `--color-border-dark` (в макете `#252A35`, совпадает без нормализации), стрелки — тёмный вариант `.slider-nav-btn--dark` (заливка `--color-bg-dark-secondary`, без рамки; на ховере полностью белый круг с тёмной иконкой — см. ниже). Карточка — фото 2:1 (пропорция через старый приём `padding-top: 50%`, не через `aspect-ratio` — причина в багфиксах ниже; та же тонировка `--color-surface-default`, что у остальных фото на сайте) над белым блоком текста.

Багфиксы после первой сборки этого блока:
- Подписи карточек были белым текстом на белой карточке и полностью пропадали: `.solutions` красит весь свой текст в белое (`color: var(--color-text-button)`) ради заголовка/описания на тёмном фоне, а `color` — наследуемое свойство, и белая карточка внутри секции наследовала его же. `.solution-card` теперь сбрасывает `color` обратно на `--color-text-primary`.
- Стрелки в шапке секции не были прижаты к правому краю — для Industries это чинилось через `margin-left: auto`, а для Solutions такое же правило забыли добавить при копировании файла. Добавлено (`.solutions__content-row .solutions__nav`).
- **Высота карточек в одном ряду плавала — потребовалось два захода.** `.solution-card` не квадратная, её высота следует за реальным количеством строк описания, а у разных карточек описания разной длины. Первая попытка — явный `align-items: stretch` на `.solutions__track` — выглядела рабочей при поверхностной проверке (несколько ширин экрана случайно давали карточкам одинаковое число строк описания), но при реальной проверке на всех брейкпоинтах (особенно на 393px и ровно на границе `xl` 1200px) карточки внутри одного ряда всё равно оставались разной высоты. Пошаговая диагностика через CDP (`getComputedStyle`, инъекция тестовых элементов в `.solutions__track`) показала: `align-items: stretch` вычисляется корректно, пустой/простой дочерний элемент в том же ряду растягивается как положено — но `.solution-card` не растягивается, если у неё **одновременно** есть картинка (`.solution-card__img-wrap`) и заполненный текстом блок (`.solution-card__info`); по отдельности каждый блок растягивается нормально, ломает именно их сочетание. Это баг Chrome, не что-то в собственной вёрстке — искать первопричину дальше не стали, а заменили `aspect-ratio: 2/1` на `.solution-card__img-wrap` на старый приём `padding-top: 50%` (сначала казалось, что дело именно в `aspect-ratio`, но это оказалось совпадением: с любым способом задать высоте картинки то же самое число, баг сохранялся). Раз чинить сам механизм stretch не имело смысла, высоту карточек теперь выравнивает JS (`equalizeHeights()` в `initSolutions`, `js/main.js`): после инициализации Swiper и на каждый resize (с debounce) высоты всех карточек сбрасываются, замеряется максимальная и проставляется явным `style.height` на все карточки — надёжно работает при любой ширине, независимо от того, чинят ли когда-нибудь этот баг в Chrome.
- **Ховер тёмной стрелки был низкоконтрастным** — `filter: brightness(1.25)` осветлял тёмный фон, но недостаточно, чтобы белая иконка поверх него читалась. Заменили на явный белый фон (`background: var(--color-bg-primary)`) с тёмной иконкой (`color: var(--color-text-primary)`) — тот же принцип, что у обычного (светлого) варианта кнопки.

## «Сервис и поддержка» (Services)

Файлы: `scss/components/_services.scss`, `_service-card.scss`. До и после секции — обычные `.spacer` (белая секция между двумя соседями, которым «оверлап»-подложка не нужна: Solutions уже скруглена со всех сторон сама по себе).

Не слайдер — колонка с заголовком/описанием слева и сетка из 6 пронумерованных карточек (`.services__grid`, CSS Grid `repeat(2, 1fr)` от `md`, 1 колонка на мобильных) справа. Раскладка в два столбца (интро + сетка рядом) включается только от `xl` — до этого интро стоит над сеткой на всю ширину, у Figma нет макета для промежуточных ширин.

- **Высота карточек в ряду сама выравнивается** — в отличие от слайдеров (Swiper, отдельная забота о `align-items`), это обычный CSS Grid, где `align-items: stretch` уже действует по умолчанию: обе карточки одного ряда растягиваются на высоту более высокой автоматически, без единой лишней строчки CSS.
- Номер — просто залитый кружок 40px (`--color-brand-primary`) с текстом, а не картинка/иконка.
- Декоративный узор из тонких линий-градиентов (`assets/services/pattern.svg`) позади текста слева — только от `xl`, в макете на других ширинах его нет. В Figma это фиксированный квадрат 748×748px, но по просьбе заказчика растянут на весь `.services__intro` (`position: absolute; inset: 0` внутри колонки + `background-size: 100% 100%`) — колонка сама растянута на высоту сетки карточек (`align-items: stretch` по умолчанию у `.services`, `display:flex` от `xl`), так что узор занимает всю левую половину блока, а не небольшой квадрат за текстом. Пропорции линий при этом слегка искажаются на нестандартных соотношениях сторон колонки — при таком количестве прозрачности это не бросается в глаза.

## «Экспертиза в области контроля...» (About)

Файлы: `scss/components/_about.scss`. Фото-фон залил сам заказчик (`assets/home-about/`, исходник 2400×1200, называние файла произвольное — `bgjpg.jpg`), затемнён тем же ffmpeg-рецептом, что CTA-фон (`eq=brightness=-0.08:contrast=1.05:saturation=0.9`), сжат в `home-about-bg.jpg`. Декоративный узор — отдельный, НЕ тот же файл, что у Services: `assets/home-about/pattern.svg`, тонкая горизонтальная линия 4% белой непрозрачности через середину (скачан из Figma по ссылке ассета, а не переиспользован по ошибке — оба узора называются в макете одинаково «Pattern», это сбивало с толку на старте).

`.about__img` получил `object-position: left center` только на мобилке (от `md` — обратно `center`): фото — широкий ландшафтный кадр с человеком в левой трети, на квадратном мобильном кропе (`aspect-ratio:1/1`) дефолтный центр обрезал его сбоку; заказчик попросил сдвинуть, чтобы человек читался в кадре целиком.

Похожая техника, что у `.cta` (см. ниже), но с важным отличием: у About в Figma реально **три** разных раскладки, не две — планшет не просто «десктоп поуже»:
- **Mobile**: фото — отдельный квадратный блок (`aspect-ratio:1/1`) с заголовком миссии («Наша миссия: уже сегодня решать задачи...»), вложенным внутрь этого фото-блока и прижатым к низу через `flex; justify-content:flex-end`. Ниже — обычная плоская белая секция (НЕ плавающая карточка: без скругления, без уголков-засечек, только `border-bottom`) с заголовком/описанием/кнопкой в нормальном потоке.
- **Tablet (md–lg)**: карточка занимает почти всю ширину секции, поэтому месту заголовку миссии сбоку взяться неоткуда — в Figma секция здесь заметно выше десктопной, и текст миссии просто идёт **под** карточкой, обычным потоком, с отступом 48px (`.about` — `display:flex; flex-direction:column; gap:48px`). Сама карточка прижата к правому краю (`.about__card{align-self:flex-end}`, только в диапазоне `md`–`xl` через `media-breakpoint-between(md, xl)`) — на узкой части диапазона (768px) это незаметно, карточка и так занимает почти всю ширину, но ближе к `1200px` разница в 400+px становится заметным пустым полем справа, если карточку не прижимать явно (по умолчанию flex-колонка выравнивает некрасиво fixed-width айтем по левому краю).
- **Desktop (xl+)**: у карточки (`max-width:678px`) есть место сбоку — `.about` становится `flex-direction:row`, карточка прижимается вправо (`margin-left:auto` у `.about__card`, не `justify-content:flex-end` у секции — см. ниже почему), а текст миссии садится к низу слева от неё (`align-self:flex-end` + `order:-1`, чтобы визуально идти первым несмотря на то, что в DOM он после карточки).

Заголовок миссии **продублирован в разметке** (тот же приём, что у стрелок слайдеров Industries/Solutions): одна копия — внутри `.about__bg`, видна только на мобилке (`d-md-none`); вторая — обычный сосед `.about__card` в DOM, видна от `md` (`d-none d-md-block`). Один текстовый узел не может одновременно быть «внутри фото-блока» на мобилке и «после карточки» на планшете/десктопе — это разные родители, а не просто другой CSS.

Два бага, найденные уже после первой сборки (заказчик проверил вживую):
- **Текст миссии нельзя было скопировать** — визуально он был поверх фото, но `.about__bg::after` (затемнение) как generated content всегда красится ПОСЛЕДНИМ среди детей `.about__bg`, то есть поверх текста, даже вложенного в разметке раньше него; 16%-й прозрачности хватало, чтобы текст читался, но не хватало, чтобы не блокировать выделение. Плюс `.about__bg` получал `pointer-events:none` от `md` (чтобы не перехватывать клики у карточки), что тоже блокировало выделение. Исправлено: `.about__mission{position:relative;z-index:1;pointer-events:auto}`.
- **На планшете (768px) текст миссии налезал на карточку** — первая версия использовала одну и ту же абсолютную позицию (`left:48;bottom:64` от `.about__bg`) что для tablet, что для desktop, но на планшете карточка занимает почти всю высоту/ширину секции и абсолютный текст оказывался у неё за пазухой. Исправление — выше (genuinely другая раскладка на tablet, поток вместо absolute). По пути ещё одна ловушка: на **desktop** в узком конце диапазона (1200–~1260px) текст миссии (486px) и прижатая вправо карточка (678px) с абсолютным позиционированием тоже могли не поместиться и наложиться — заменили `justify-content:flex-end` + absolute на чистый flex (`margin-left:auto` у карточки, `flex-shrink:0`, обычный `order:-1`/`align-self:flex-end` у текста без absolute) — при нехватке места текст миссии просто переносится на лишнюю строку, а не накладывается. Проверено через CDP: площадь пересечения прямоугольников текста и карточки = 0px² на всём диапазоне 1200–1920, включая точки 1200/1230/1260.

Заголовок карточки — `h1`/`--h1-size` (40/48 desktop → 24/32 mobile по общей шкале типографики), не `--color-text-heading`, а `--color-text-primary` — как и у `.cta__title`, то же расхождение с макетом. Кнопка — обычный `.btn.btn-primary.btn-lg` с добавленной стрелкой (`icon` sprite `arrow-right`, уже был в спрайте, из Figma тащить не пришлось) через `display:inline-flex;gap:12px`. Декоративная линия-паттерн — фиксированный размер 1600×752 (не тянется под бокс, просто центрируется и обрезается `overflow:hidden` секции), от `md` и только там, в Figma на мобилке её нет.

Описание — два абзаца с пустой строкой-разделителем в макете; вместо пустого `<p>` — явный `margin-bottom:16px` у первого абзаца (через `.about__description p:first-child`, БЕЗ класса `.mb-0` на самом `<p>` — Bootstrap-утилита `!important` иначе перебивает это правило).

Проверено через CDP на 393/768/1920 (скриншоты, сверены с Figma-рендерами всех трёх фреймов) и на консоль (чисто, без ошибок и 404 по картинкам).

## AboutBullets (4 буллита под About)

Файлы: `scss/components/_about-bullets.scss`. Идёт СРАЗУ после `.about`, **без `.spacer` между ними** — заказчик явно попросил считать это продолжением блока About, а не отдельной секцией. 4 карточки (иконка-иллюстрация + название + описание) на светло-сером фоне (`--color-bg-secondary`).

Раскладка по брейкпоинтам — база взята из Figma (через `get_metadata` по каждому фрейму отдельно: `get_design_context` у Figma MCP вернул ОДИНАКОВЫЙ код для всех трёх node id, тот же баг сервера, что уже был на About), но брейкпоинт перехода в один ряд сдвинут по просьбе заказчика:
- **Wide desktop (`xxl`, от 1400px)**: одна строка (`display:flex;flex-direction:row`), `.about-bullet{flex:1 1 0}`.
- **Tablet и «обычный» desktop (`md`–`xl`, 768–1399px)**: сетка 2×2 (`display:grid;grid-template-columns:repeat(2,1fr)`). В Figma это раскладка tablet-фрейма, но заказчик попросил держать её вплоть до `1400px` — на 1200–1399 (стандартный `xl`, где обычно у других блоков сайта уже начинается «широкий» вид) один ряд из 4 получался слишком тесным, картинки едва помещались.
- **Mobile**: одна колонка.

**Карточки НЕ квадратные** — первая версия форсировала `aspect-ratio:1/1` на любом разрешении, но это потребовало сжимать картинку до 0px и обрезать длинные описания через `-webkit-line-clamp` на тесных ширинах (например ровно `1200px`, где ряд уже 4-колоночный, а карточка ещё маленькая). Заказчик явно попросил откатить: без обрезки текста, без сжатия картинки, карточки просто **вытягиваются по вертикали**, когда контенту нужно больше места. Сейчас высота — обычная, по контенту (заголовок + описание + картинка своей естественной пропорции 322:148, никакого `aspect-ratio`/`overflow:hidden` на самой `.about-bullet`).

Одинаковая высота карточек в одном ряду/сетке (чтобы ряд не выглядел рваным) обеспечивается **не через CSS**, а через JS: `equalizeAboutBullets()`-подобная IIFE в `js/main.js` (тот же приём, что `equalizeHeights()` у Solutions) — меряет реальную высоту каждой карточки и выставляет всем максимальную явным `style.height`. Не `align-items:stretch`, потому что у `.about-bullet` та же комбинация (картинка+текст в одном flex-item), что и раньше ломала stretch в Chrome — см. секцию Solutions выше. На мобилке (одна колонка, `window.innerWidth < 768`) выравнивание НЕ применяется — там высоты у карточек разные, по контенту, как и в Figma.

Картинки всегда прижаты к низу карточки и на одном уровне друг с другом — `.about-bullet{justify-content:space-between}` (текст сверху, картинка снизу, с ростом свободного места между ними). Работает именно потому, что высоты карточек в ряду уже выровнены JS-ом выше: раз все карточки одной высоты и одной ширины (а у картинки фиксированная пропорция 322:148), низ и верх картинок автоматически совпадают у всех карточек в ряду — без выравнивания высоты `space-between` просто прижимал бы картинку к разному Y на каждой карточке.

Картинка — `object-fit:contain` внутри `.about-bullet__img-wrap{aspect-ratio:322/148}` (не `cover` и не индивидуальный %-кроп из самой первой версии): полностью видна, без обрезки и искажений. PNG-иллюстрации (`assets/about-bullets/img1-4.png`, скачаны из Figma, были 1774×887, пересжаты в 900px шириной) прозрачные (проверено через ffmpeg — угловой пиксель `rgba(0,0,0,0)`), поэтому "letterboxing" у `contain` не виден вообще; рисуются с `opacity:0.64`.

Название карточки — `h5`, цвет `#1a1d21` из макета нормализован до `--color-text-heading`, та же логика, что у `.industry-card__name`/`.category-card__title`. Описание — обычный body-текст (14/20 по умолчанию, без доп. класса), без ограничения по числу строк.

Проверено через CDP на 320/393/768/1024/1199/1200/1920: на мобилке высоты разные по контенту, от `md` — все карточки в ряду/сетке строго одной высоты и заметно вытянуты по вертикали (например на 1200px — 266×433), ни один текст не обрезан (`scrollHeight === clientHeight` у описания везде), консоль чистая.

## Logos («Клиенты и партнеры»)

Файлы: `scss/components/_logos.scss`. Заголовок+описание сверху, ниже — бесконечная лента логотипов.

**Крутится на всех брейкпоинтах, включая desktop** — в Figma desktop-фрейм показывает все 6 логотипов статично умещающимися в ряд без скролла (на tablet/mobile ряд шире контейнера, с очевидно "прокрученным" смещением — это состояние карусели, а не статичная раскладка), но заказчик явно попросил анимировать ленту везде, раз это называется «карусель логотипов». Крутится через CSS `@keyframes` (`.logos__track{animation:logos-scroll 32s linear infinite}`), не через Swiper — здесь не нужны ни стрелки, ни свайп, ни какое-либо взаимодействие: просто нескончаемая прокрутка, для которой чистый CSS transform-анимация дешевле по производительности, чем настраивать под это отдельный Swiper-инстанс с autoplay. Ряд логотипов продублирован в разметке ровно два раза подряд — анимация сдвигает на `-50%` собственной ширины (что равно ширине ОДНОГО набора), и цикл получается бесшовным без JS-подсчёта. Копии-дубли — `aria-hidden="true"`, `alt=""` (декоративные, из доступности исключены). На `:hover` анимация ставится на паузу (`animation-play-state:paused`) — удобно разглядеть конкретный логотип; на `prefers-reduced-motion:reduce` анимация выключена совсем.

Плавное исчезновение по краям через `mask-image: linear-gradient(...)` на `.logos__track-wrap` — без него лента обрывается резкой границей ровно по краю секции, для бесконечной прокрутки это читается менее убедительно.

Декоративный паттерн (`assets/logos/pattern.svg`, две полу-окружности + расходящиеся линии, `#F1F4FA`, еле заметный — тот же принцип прозрачности, что у Services/About) — ширина 100% секции (растянута, не фиксированная 1600px — см. багфикс ниже), высота фиксированная 800px (реальный размер ассета по вертикали), **прижат к нижнему краю** секции (`bottom:0`, не `top:50%`/`center` как в About) — у самого SVG центр обеих окружностей находится на нижней границе вьюбокса, так что если центрировать паттерн вертикально, на узких экранах (где вся секция может быть значительно ниже 800px) как раз обрежется "источник" дуг снизу.

- **Багфикс: паттерн не был виден вообще.** Первая версия ставила ему `z-index:-1`, рассчитывая просто увести декор под остальной контент секции — но `.logos` сам не формирует собственный stacking context (нет своего `z-index`, только `position:relative`), а значит отрицательный `z-index` ребёнка "убегает" в ближайший АНЦЕСТОРНЫЙ stacking context выше по дереву — паттерн физически проваливался куда-то не туда и не был виден вообще ни на одном брейкпоинте. Исправлено тем же приёмом, что и `.about__mission`: `z-index` у паттерна убран целиком (остаётся `auto`, в нормальном порядке — он первый в DOM), а `.logos__header`/`.logos__logo-container` получили явные `position:relative;z-index:1` — гарантированно выше паттерна, без сюрпризов со stacking context.
- **Высота декоративной зоны под лого — из Figma, не была скопирована в первой версии.** "Logo Container" в Figma — это не сама лента логотипов (она остаётся ~72px высотой), а большая зона ПОД неё для воздуха вокруг паттерна: 136px mobile / 168px tablet / **600px desktop**. Добавлен отдельный `.logos__logo-container{height:136px}` (168 от `md`, 600 от `xl`) с `align-items:center;justify-content:center` — лента просто центрируется в этой зоне по вертикали, а не растягивается сама.

6 логотипов (`assets/logos/*.svg`, скачаны из Figma по ссылкам ассетов: gazprom/liangong/elcometer/arun/rzd/tyazhmash) — высота у каждого своя, задана явно по модификатор-классам (`.logos__item--gazprom{height:72px}` и т.п.), ширина не задаётся — берётся по собственной пропорции SVG (viewBox некоторых исходников чуть отличается от заявленных в макете px, жёсткая ширина исказила бы пропорции). В Figma лента не масштабируется под ширину экрана вообще (одни и те же px на всех брейкпоинтах), но по просьбе заказчика на мобилке логотипы уменьшены в полтора раза против макета (72→48, 64→43, 32→21, 48→32) — макетный размер на узком экране выглядел слишком крупным; от `md` — обратно на Figma-размеры.

Проверено через CDP на 393/768/1920: паттерн и логотипы грузятся без 404, паттерн реально виден на всех трёх ширинах (дуги/линии на скриншотах), высота `.logos__logo-container` ровно 600px на десктопе, лента реально движется (`getBoundingClientRect().left` меняется во времени), консоль чистая.

**Свайп пальцем на мобилке — заказчик попросил дать управлять лентой вручную, хотя изначально её делали специально БЕЗ какого-либо взаимодействия («просто нескончаемая прокрутка», см. выше).** Автопрокрутка через CSS transform-анимацию и ручной `scrollLeft` через touch принципиально не сочетаются — если оставить оба активными одновременно, они бы одновременно двигали контент по-разному (анимация продолжает ехать сама по себе, а палец пытается задать свою позицию), что ощущалось бы как рывки и борьба между собой, а не отзывчивый свайп. Поэтому изменения применены ТОЛЬКО на мобилке (`media-breakpoint-down(md)`, <768 — планшет и десктоп не тронуты, там по-прежнему автопрокрутка): `.logos__track-wrap` вместо `overflow:hidden` получает `overflow-x:auto` (+`-webkit-overflow-scrolling:touch`) — становится настоящим горизонтальным скролл-контейнером; `.logos__track{animation:none}` — авто-анимация выключена, чтобы не конфликтовать с ручным скроллом. Скроллбар спрятан визуально (`scrollbar-width:none` + `::-webkit-scrollbar{display:none}`) — сам скролл работает, просто без видимого трека, обычный приём для карточных/логотипных лент. Разметка не менялась — она уже была задублирована вдвое ради бесшовной анимации, и это не мешает ручному свайпу, просто даёт прокрутить чуть дальше до повтора набора.

Проверено через CDP на 393: `overflow-x:auto` и `animation-name:none` подтверждены computed-стилями, `scrollWidth` (1615) больше `clientWidth` (361) — контейнер реально скроллится; симулирован НАСТОЯЩИЙ touch-жест через `Input.synthesizeScrollGesture` (не программальное присвоение `scrollLeft`, а честная эмуляция пальца) в обе стороны — `scrollLeft` сдвинулся 0→202 при свайпе влево, затем 202→85 при свайпе вправо обратно; скриншоты до/после подтверждают, что видимый набор логотипов реально меняется. На 834 (планшет) отдельно проверено, что `.logos__track` продолжает двигаться сама по себе во времени (автопрокрутка не тронута) — консоль чистая на обоих вьюпортах.

## Подвал (Footer)

Файлы: `scss/components/_footer.scss`. Три «полосы» (бренд-строка, ссылки на категории, реквизиты), с одним и тем же вертикальным разделителем по центру, проходящим через все три полосы на любом брейкпоинте (tablet/desktop) — этого не видно ни на одном отдельном скриншоте Figma, но подтверждается сквозным совпадением X-координаты границы во всех трёх «container» на 34:1417/38:2382.

**Реализация через CSS Grid с одинаковым паддингом у каждой колонки, а не буквальным повтором Figma-вложенности.** В Figma каждая полоса физически состоит из двух «половин» (каждая — свой `flex` с `gap-48` между двумя внутренними колонками и `p-48` по периметру), из-за чего расстояние между колонками 1↔2 и 3↔4 (48px, «внутри половины») формально меньше расстояния между 2↔3 (по факту ~96px — паддинг правого края половины 1 + паддинг левого края половины 2, но безо линии-разделителя). Повторять эту вложенность буквально не стал — вместо этого у `.footer__col` **везде одинаковый** `padding:48px`, без отдельного `grid-gap`; за счёт удвоенного соседнего паддинга colonки визуально расставлены даже равномернее, чем в макете (там 2↔3 было чуть просторнее остальных) — разница на глаз не читается, а разметка сильно проще: плоская сетка вместо вложенных «половин».

- **Desktop (`xl`)**: `grid-template-columns:repeat(4,1fr)` — Контакты/НК/МехИсп/Анализ в один ряд. Разделитель только один — `border-right` на 2-й колонке (`nth-child(2)`), это и есть центр.
- **Tablet (`md`–`lg`)**: `repeat(2,1fr)` — сетка автоматически заворачивает 4 колонки в 2×2 (Контакты+НК в первой строке, МехИсп+Анализ во второй) без каких-либо доп. обёрток в разметке, просто следствие того, как CSS Grid переносит элементы. Разделитель — `border-right` на нечётных колонках (`nth-child(odd)`, 1-й и 3-й, между парами в каждой строке) + `border-top` на 3-й/4-й (`nth-child(n+3)`, разделяет сами строки).
- **Mobile**: одна колонка, разделителей нет.

**Цвета — два новых токена, не Figma-значения впрямую.** У Figma здесь `bg/light` = `#eff0f3` (фон подвала) и `border/light` = `#f1f4fa` (внутренние линии) — сами по себе эти два значения различаются всего на пару единиц на канал, поэтому в реальном Figma-рендере разделители практически не видны (проверено скриншотом самого макета — на глаз ни одной внутренней линии не различить). Учитывая более раннее явное пожелание заказчика сделать разделители на сайте контрастнее (см. историю `--color-border-light`, было `#f1f4fa` → стало `#eff0f3` из-за этого же запроса), для подвала взял **уже существующий `--color-border-default`** (`#dce2f1`, тот же токен, что у разделителей каталога/Industries) вместо повторного введения еле заметного `#f1f4fa` — линии в подвале в итоге чётко видны, а не почти прозрачны, как в оригинале. Фон подвала — новый токен `--color-bg-footer` (`#eff0f3`, добавлен в `$stc-colors`, т.к. ни один существующий `bg-*` токен не совпадает достаточно близко: `bg-light` — это `#fafbfd`, совсем другое значение под другую задачу).

**Логотип** переиспользует те же `assets/logo.svg`/`logo-text.svg` и mask-приём, что и `.header__logo-mark`/`.header__logo-text` — просто крупнее (84×56/120×40 на мобилке, 96×64/144×48 от `md`), новых ассетов не потребовалось.

**Мобильный аккордеон.** Три категории (Неразрушающий контроль / Механические испытания / Анализ металлов) на мобилке сворачиваются, «Контактная информация» — всегда открыта (без шеврона, без клика), это видно по метаданным mobile-фрейма: только у трёх категорий есть `angle-down`/`angle-up`. `-webkit-line-clamp` тут ни при чём — раскрытие через приём `grid-template-rows: 0fr → 1fr` (современный CSS-способ плавно анимировать до `auto`-высоты без JS-измерения `scrollHeight`; непосредственный ребёнок грида обязан иметь `overflow:hidden`, иначе схлопывание не работает). JS (`js/main.js`) только переключает класс `.is-open` и `aria-expanded` по клику на `.footer__col-toggle` — **без проверки ширины экрана**: выше `md` CSS сама держит `grid-template-rows:1fr` всегда и прячет шеврон (`media-breakpoint-down(md)` — единственное место, где раскрытие вообще что-то значит), так что клик на десктопе просто не даёт видимого эффекта, а не требует отдельной JS-ветки.

**Другой порядок блока «Контактная информация» на мобилке.** В Figma на мобильном фрейме этот блок идёт ПОСЛЕДНИМ (после всех трёх аккордеонов), а на tablet/desktop — ПЕРВЫМ. Решено через CSS `order` вместо дублирования разметки: в DOM блок физически идёт последним (совпадает с mobile-порядком по умолчанию), `.footer__col--contact{order:-1}` от `md` визуально переставляет его в начало. Была реальная ошибка на первом проходе — по невнимательности вписал «Контактную информацию» первой и в DOM тоже, из-за чего на мобилке она внезапно оказалась первой (расходясь с Figma) — поймано и исправлено сразу при сверке со скриншотом.

Категории ссылаются на `catalog.html` (как и карточки каталога на главной), телефон/почта — настоящие `tel:`/`mailto:` ссылки, «Наверх» — просто `href="#"` (у `html` уже стоит `scroll-behavior:smooth` из шапки, так что переход наверх сам получается плавным, JS не понадобился).

Ещё два багфикса:

Правильная форма техники требует **двойной** вложенности: `.footer__col-collapse` (грид, `0fr`/`1fr`) → `.footer__col-collapse-inner` (только `overflow:hidden;min-height:0`, без единого отступа) → `.footer__col-list` (сам список, со своими отступами уже внутри `-inner`, где они честно обрезаются). Добавлена промежуточная обёртка в разметке всех трёх аккордеонов. Проверено: `grid-template-rows` в свёрнутом состоянии теперь реально `0px` (было `16px`), позиция кнопки от верха колонки равна расстоянию до низа (`24px` = `24px`).

Это осознанное упрощение под статический сайт, а не недосмотр.

Стили карточки результата (`.search-result:hover{background:var(--color-bg-footer)}`) переиспользуют тот же токен `#eff0f3`, что и `.wiki-card:hover` — тот же принцип переиспользования близких/совпадающих hex вместо новых токенов.

**Баг после первой сборки: тёмная подложка (`--color-surface-popup`, `rgba(0,0,0,.5)`) не была видна на скриншоте — только белый фон.** Причина — `.search-overlay.is-open{display:flex; justify-content:center}` без явного `align-items` брал дефолтный `stretch`, из-за чего белая `.search-panel` растягивалась на всю высоту оверлея (826px), а не только на высоту своего контента (~144px), и просто перекрывала собой всё затемнение. Исправлено добавлением `align-items: flex-start` — панель теперь занимает только контентную высоту, а тёмная подложка честно видна под/вокруг неё. Проверено через CDP на 1920/834/393: `panelHeight` (144/144/184px) заметно меньше `overlayHeight` (826/926/788px), `background-color` оверлея — `rgba(0, 0, 0, 0.5)`, консоль чистая на всех трёх. В состоянии с результатами панель, наоборот, закономерно растягивается почти на всю высоту (контента много, `panelHeight` может даже превышать `overlayHeight` — тогда работает `overflow-y:auto` самого оверлея) — это ожидаемо и не баг.

Прочая проверенная функциональность (CDP): фокус в поле при открытии, клик по тегу заполняет поле и показывает результаты, крестик очистки поля сбрасывает и поле, и результаты, `Escape` и клик по подложке закрывают панель.

Правки после первой сборки (заказчик проверил вживую):
- **Ховер тега-подсказки** сменён с заливки фона на плавное приглушение непрозрачности (`opacity:0.6`, `transition .15s`) — тот же приём, что у `.tab` в фильтре каталога, вместо точечного отдельного решения.
- **Прыжок скролла при открытии.** Раньше блокировка страницы за оверлеем делалась через `document.body.style.overflow='hidden'`, что убирало нативный скроллбар и сдвигало весь контент (включая шапку) вправо на его ширину — заметный «прыжок» при каждом открытии/закрытии. Разобрался в два шага: (1) `html{scrollbar-gutter:stable}` резервирует место под скроллбар всегда, но работает только пока `overflow-y` не `visible` — добавил `overflow-y:auto` на `html`, которая и так фактический скролл-контейнер страницы; (2) даже с этим `overflow-y` дальше нельзя было переключать в `hidden` через JS — проверено через CDP, что именно значение `hidden` (в отличие от `auto`) сбрасывает зарезервированный gutter обратно в 0, так что сам смысл резервации терялся в момент блокировки. Вместо переключения `overflow` заменил блокировку на классический приём `body{position:fixed; top:-scrollY}` (сохраняет `scrollY` в `open()`, восстанавливает через `window.scrollTo` в `close()`) — `html` при этом вообще не трогается, его `overflow-y:auto`+`scrollbar-gutter:stable` остаются постоянными и никогда не переключаются, so сам скроллбар/gutter не мигает. Проверено через CDP на 1920: `.header`/`.search-overlay` `getBoundingClientRect()` даёт одинаковую ширину (1905px) и до, и после открытия панели — нулевой сдвиг; отдельно проверено, что после закрытия `window.scrollY` возвращается к значению до открытия (протестировано с предварительным скроллом на 1200px). `document.documentElement.clientWidth` при этом продолжает показывать разные числа (1905/1920) — это ожидаемо, `clientWidth` по определению не включает зарезервированный gutter, но сам видимый layout (`offsetWidth`/`getBoundingClientRect`) не меняется, так что реального визуального прыжка нет.
- **Баг сразу следом: заказчик заметил, что при закрытии (со скролла вниз) страница резко прыгала наверх, а затем плавно уезжала назад к исходной позиции.** Причина — тот же самый общий подвох, что уже документирован в разделе про Footer/про технику CDP-проверки: `html{scroll-behavior:smooth}` глобально анимирует ЛЮБОЙ `window.scrollTo`, включая программное восстановление позиции в `close()`. Плюс сам приём `body{position:fixed}` попутно даёт побочный эффект — пока `body` вне потока, `document.scrollHeight` схлопывается до высоты вьюпорта, и браузер молча обнуляет `window.scrollY` (визуально это не видно — `body{top:-scrollY}` компенсирует картинку — но сам внутренний scrollY реально становится 0). Когда `close()` убирает `position:fixed`, страница на долю кадра реально оказывается в состоянии scrollY=0 (реальный, не визуальный сброс) — а следующий `window.scrollTo(0, scrollY)` из-за глобального `scroll-behavior:smooth` не прыгает мгновенно назад, а плавно ползёт вверх → вниз, что и читается как «дёрнуло наверх и вернуло». Фикс: `window.scrollTo({top:scrollY, left:0, behavior:'instant'})` — явный `behavior:'instant'` в объекте-опциях переопределяет CSS `scroll-behavior` (в отличие от старой двухаргументной формы `scrollTo(x,y)`, которая CSS-анимацию не может игнорировать). Проверено через CDP: значения `window.scrollY`, снятые синхронно в цикле сразу после клика на закрытие (8 замеров подряд, без ожидания между ними), все идентичны целевой позиции (1051px, было проскроллено туда заранее) — то есть восстановление мгновенное, ни одного промежуточного кадра с других значением, консоль чистая.

Не закоммичено на момент записи.

**Ещё два фидбека сразу после (заказчик проверил вживую).** (1) При закрытии поиска на прокрученной странице шапка резко пропадала и появлялась заново. Причина — тот же скролл-лок: пока `body{position:fixed}`, `window.scrollY` молча обнуляется браузером, и НЕСВЯЗАННЫЙ скролл-слушатель шапки (`.header--stuck`) реагировал на это, снимая класс в фоне (невидимо, пока поиск сверху), а сразу после закрытия и мгновенного восстановления scrollY получал его обратно — этот один кадр без класса читался как «шапка исчезла и появилась». Фикс — ранний выход из `apply()` в скролл-слушателе шапки, пока `document.body.style.position === 'fixed'`. (2) Добавлена анимация выезда — `display:none/flex` заменён на `opacity+visibility` (переключение visibility с разной задержкой на открытии/закрытии, чтобы панель пропадала из хит-теста только ПОСЛЕ анимации, а не раньше), сама `.search-panel` получила `transform:translateY(-24px → 0)` — плавно выезжает сверху при открытии и уезжает обратно при закрытии, `prefers-reduced-motion` отключает transition. Проверено через CDP: `header--stuck` за весь цикл открытие→закрытие меняется ровно 0 раз (MutationObserver лог пустой после первого состояния), opacity/transform корректно анимируются через промежуточные кадры (~60мс: opacity≈0.22, translateY≈-18.7px) и доезжают до конечных значений, фокус/видимость переключаются как раньше, консоль чистая.

**Отказ от `scrollbar-gutter:stable` на `.search-overlay` — по явной просьбе заказчика.** Это свойство держало постоянный резерв (~15px) под скроллбар на правом краю оверлея, даже когда сам скроллбар не нужен (короткий список без прокрутки) — решение было принято раньше специально, чтобы избежать скачка центрированного контента при появлении/исчезновении скролла (см. записи выше про двойной отступ/формулу компенсации). Заказчик посмотрел вживую и явно попросил другое: белый фон панели должен доставать строго до истинных левого и правого краёв экрана в пустом состоянии, без всякого резерва — даже ценой того, что при реально длинном списке результатов (когда скроллбар появляется) контент может слегка сдвинуться. `scrollbar-gutter: stable` убран с `.search-overlay` полностью. Проверено через CDP на 1920: в пустом состоянии `clientWidth` оверлея — `1920` (ровно вьюпорт, `scrollbarGutter:"auto"`, резерва нет); после клика по тегу-подсказке (20 демо-результатов, реальный скролл появляется) `clientWidth` закономерно сужается до `1905` (настоящий скроллбар, не фантомный резерв) — скриншоты подтверждают: в пустом состоянии у правого края чистый белый фон вплотную к краю экрана, при скролле справа рисуется обычный трек без второй полосы рядом.

**Тот же компромисс пересмотрен ещё раз: заказчик захотел оба свойства сразу** — фон во всю ширину при обычном открытии, но БЕЗ скачка контента при появлении результатов/скролла. Первая попытка — переключать `scrollbar-gutter:stable` динамически через класс `.search-overlay--has-results` (включать ровно в момент появления результатов, не раньше и не по факту скролла) — оказалась НЕ РАБОЧЕЙ: заказчик заметил, что скачок никуда не делся, просто переехал в другой момент. Причина в самой логике: `scrollbar-gutter` (постоянно или условно — не важно) меняет ширину КОНТЕНТ-БОКСА `.search-overlay`, а `.search-panel` был завязан на неё через `width:100%` — любое изменение этой ширины (когда бы оно ни случилось: сразу, при открытии, или при появлении результатов) неизбежно двигало центрированный `.search-panel__inner`. Настоящее решение — разорвать эту зависимость полностью: `.search-panel{width:100vw; flex-shrink:0}` вместо `width:100%` — `100vw` берётся от истинного размера вьюпорта и не зависит от того, сузил ли `.search-overlay` свой контент-бокс под собственный скроллбар; `flex-shrink:0` обязателен отдельным пунктом — без него flexbox по умолчанию всё равно сжал бы явную ширину под фактически доступное (уже суженное) место в родителе, сводя весь приём на нет. `.search-overlay` при этом сменил `justify-content:center` на `flex-start` — с `center` избыток ширины (когда панель 1920px шире контент-бокса 1905px) распределялся бы симметрично в обе стороны (часть панели уезжала бы за левый край, а до правого при этом не доставала); `flex-start` прижимает панель к левому краю, весь излишек уходит вправо — ровно в ту зону, которую `overflow-x:hidden` потом обрезает, и где физически сидит скроллбар, когда он есть. Итог: `.search-panel` и `.search-panel__inner` теперь имеют АБСОЛЮТНО одинаковые координаты в любом состоянии — пустом, при каждом нажатии клавиши, с полным списком результатов, после очистки поля. Проверено через CDP на 1920 (посимвольная имитация ввода "Ультра", 6 промежуточных замеров + открытие/очистка/клик по тегу): `.search-panel` во всех случаях `{left:0, right:1920, width:1920}`, `.search-panel__inner` во всех случаях `{left:621, right:1299}` — идентично, без единого отличающегося замера. Проверено также на 393/834 (мобилка/планшет) — консоль чистая везде.

**Попутно найденный баг: на мобилке поле ввода и теги-подсказки упирались прямо в край экрана, без бокового отступа.** Заказчик заметил, что у `.search-panel__inner` «пропали пэдинги по бокам по 16px» — на деле их там никогда и не было явно: на tablet/desktop иллюзию отступа создавало исключительно центрирование `max-width:678px` внутри более широкой панели (`.search-panel{justify-content:center}`), а на mobile, где вьюпорт уже 678px, `.search-panel__inner{width:100%}` заполнял всю ширину панели без остатка — а сама `.search-panel` намеренно без своего левого/правого паддинга (белый фон должен доходить до истинных краёв экрана, см. записи выше). Добавлен `padding: 0 16px` НА САМ `.search-panel__inner` — теперь боковой отступ есть всегда и везде, независимо от того, работает ли в моменте центрирование или нет; на desktop/tablet эффект нейтральный (чуть уменьшает и без того центрированную контентную область, визуально почти незаметно). Проверено через CDP: на 393px `.search-panel__row` теперь `{left:16, right:377}` (было `{left:0, right:393}` — вплотную к краям), на 834/1920 — без изменений в восприятии, стабильность (без скачков при вводе) из предыдущего фикса не нарушена.

**Только десктоп (`xl`+), без брейкпоинтов вообще.** Сам триггер уже был скрыт до `xl` (`d-none d-xl-flex`, часть исходной вёрстки шапки) — на планшете/мобилке каталог переедет в гамбургер-меню отдельной задачей, а пока там наведение на скрытый триггер просто невозможно, и это меню там никогда не откроется. Проверено: `display:none` на 768px подтверждён через CDP.

**В отличие от поиска, оверлей НЕ перекрывает шапку** (`top:var(--header-h)`, а не `top:0`). Здесь это принципиально: триггер открытия сам живёт внутри шапки, и если бы меню накрывало её собой, курсор в момент появления меню терял бы наведение на «Каталог» и оно тут же закрывалось само. Тот же приём с `opacity+visibility+transform`, что и в поиске (см. выше) — сайдбар плавно выезжает по X (-24px → 0), задержка на `visibility` только при закрытии.

**Структура повторяет Figma 1-в-1**: слева — сайдбар 393px с тремя категориями-аккордеонами (grid-template-rows:0fr→1fr, та же двойная обёртка `-inner` без своих отступов, что и в аккордеоне подвала — тот же баг схлопывания уже был найден и задокументирован там); справа — плавающая панель (высота по контенту, НЕ растянута на всю высоту сайдбара — `align-items:flex-start` у родителя) с шапкой (иконка+заголовок), пилюльными табами (переиспользован `.tabs`/`.tab` от фильтра каталога главной — совпадают все размеры/цвета кроме шрифта, там 12px вместо 14, переопределено точечно) и двумя рядами карточек товаров (4+3, `align-items:flex-start` — карточки НАМЕРЕННО разной высоты, как в самой Figma, без выравнивания в отличие от Solutions/AboutBullets).

Заодно (отдельные просьбы): opacity-hover у «Поиска»/«Сравнения» (см. выше) уточнён — должен был красить ТОЛЬКО фон, а не всю кнопку целиком (включая иконку и бейдж-счётчик). **Баг найден по скриншоту с Mac: горизонтальный скролл в сайдбаре catalog-menu при наведении на «Радиографический контроль».** В headless Chrome не воспроизвёлся (`scrollWidth === clientWidth` и до, и после наведения, попунктово проверил ширину дочерних элементов строки — переполнения нет). Та же категория «видно только на реальном Mac», что и артефакт с обводками `.icon-btn` ранее. Причина, скорее всего: `overflow-y:auto` без явного `overflow-x` — по CSS-правилу браузер сам вычисляет `overflow-x` как `auto` (не `visible`), если `overflow-y` не `visible`, так что ЛЮБОЕ горизонтальное переполнение хоть на 1px (сабпиксельное округление, специфичное для движка/дисплея) сразу рисует скроллбар. Защитный фикс — явный `overflow-x:hidden` на `.catalog-menu__sidebar`, `.catalog-menu__content` и `.search-panel` (все три — новые скролл-контейнеры) — гарантированно убирает саму возможность горизонтального скролла, независимо от точной причины переполнения.

Проверено через CDP: `lockPageScroll`/`unlockPageScroll` работают идемпотентно и симметрично; `.search-panel` — реальный скролл-контейнер с 20 результатами, без горизонтального overflow; `.catalog-menu__sidebar`/`.catalog-menu__content` оба `overflow-x:hidden`. Консоль чистая на 393/834/1920.

**Скролл поиска возвращён обратно на `.search-overlay`, без кастомной тонкой стилизации.** После нескольких итераций (сначала оверлей → потом «в рамках search-panel» с тонким скроллбаром) заказчик прямо уточнил: хочет ОБЫЧНЫЙ браузерный трек (не тонкий кастомный) в ОБЫЧНОМ месте — там же, где обычно скроллится сама страница (у истинного правого края экрана), просто когда поиск открыт, именно эта прокрутка скроллит поиск, а не страницу за ним. Убран `@include thin-scrollbar` и `overflow-y`/`max-height` с `.search-panel`, всё вернулось на `.search-overlay` (`overflow-y:auto`, обычный вид). `overflow-x:hidden` на оверлее оставлен как защита от горизонтального переполнения (тот же класс бага, что нашли в catalog-menu на Mac). Проверено через CDP: `.search-overlay` скроллится (`scrollHeight:1516 > clientHeight:900` с 20 результатами), `scrollbar-width` вычисленно `auto` (не `thin`), горизонтального overflow нет.

**Та же логика применена к catalog-menu — сайдбар и панель тоже вернули на обычный трек, но с оговоркой.** Заказчик: «я бы и в сайдбаре вернул обычный трек скролла и убрал бы отступы — сделал в плотную, но только чтобы во втором уровне меню грид не прыгал при появлении скролла». То есть: убрать тонкую кастомную стилизацию отовсюду в catalog-menu (для единообразия с поиском), НО для правой панели («второй уровень меню») сохранить сам механизм, защищающий от прыжка сетки при появлении скролла.

- **`.catalog-menu__sidebar`**: `@include thin-scrollbar` убран, вернулся обычный `scrollbar-width:auto`. Никакого специального запаса под ширину там не было и не появилось — сайдбар реально почти никогда не скроллится, так что «прыжок» здесь не практическая проблема (в отличие от панели, где сценарий демонстрировался на реальных 24 карточках).
- **`.catalog-menu__content`**: `@include thin-scrollbar` тоже убран, но ширина внешнего скролл-слоя (`.catalog-menu__content`, отдельного от видимой карточки `-inner`) увеличена с 794px обратно до 808px (784 карточка + 24 запас) — стандартный системный скроллбар (особенно на Mac с «Показывать всегда») может быть заметно шире тонкого кастомного (8px), запас взят с бо́льшим допуском (24px), чтобы гарантированно вместить его, не трогая саму карточку. Сам двухслойный механизм (внешний скролл-контейнер + внутренняя фикс-ширины карточка `.catalog-menu__content-inner`, 784px) остался как есть — это и есть та часть, которую заказчик попросил сохранить.

Проверено через CDP: `scrollbar-width` и у сайдбара, и у панели вычисленно `auto`; карточка контента (`.catalog-menu__content-inner`) остаётся ровно 784px и на коротком гриде («Капиллярный контроль»), и на 24-карточечном демо со включённым скроллом («Радиографический контроль», `hasVerticalScroll:true`); горизонтального overflow нет (`hasHorizontalOverflow:false`). Консоль чистая на 393/834/1920.

**Статичный запас (24px) убрали — заказчик прислал скриншот, там видна щель между карточкой и скроллбаром.** Заранее прикинутое число (24px) не совпадало с реальной шириной скроллбара конкретного браузера/ОС — либо оставалась пустая полоса (запас больше факта), либо (в другом браузере) скроллбар начал бы обрезать карточку (запас меньше факта). Правильное решение — не гадать, а измерить: новая мини-IIFE в начале `js/main.js` создаёт временный `div{overflow:scroll}` с внутренним `div`, разница `offsetWidth`-`innerOffsetWidth` — это и есть реальная ширина скроллбара текущего браузера, кладётся в CSS-переменную `--scrollbar-width` на `:root` один раз при загрузке страницы. `.catalog-menu__content{width:calc(784px + var(--scrollbar-width, 15px))}` — запас теперь точно равен факту, без произвольного числа (15px в `calc()` — просто fallback на случай, если переменная почему-то не успела выставиться). Заодно убран `margin-right:2px` с `.catalog-menu__content-inner` — он был частью старой ручной подгонки под конкретную (тонкую) ширину скроллбара и с точным измерением больше не нужен: карточка и обычный скроллбар теперь стыкуются впритык, без зазора и без обрезания.

Проверено через CDP: `--scrollbar-width` в headless Chrome измерился как `15px`; `.catalog-menu__content` `clientWidth` (784) точно совпадает с шириной карточки (`.catalog-menu__content-inner`, тоже 784) — то есть карточка занимает ВЕСЬ доступный контент-бокс до самого скроллбара, без щели и без обрезания; `offsetWidth` (799) на 15px больше, что соответствует измеренной ширине скроллбара. Консоль чистая на 393/834/1920.

**Поиск: контент прыгал влево при появлении скролла (много результатов) — реальный баг, найден и исправлен.** Заказчик заметил два связанных симптома: справа при скролле появлялось «некрасивое белое пространство», а сам центрированный контент (поле ввода/теги/результаты) заметно смещался влево. Причина: `.search-panel{width:100%}` — 100% от content-box `.search-overlay`, который у коротких результатов (без скролла) занимает всю ширину экрана, а у длинных (скролл включился) сужается примерно на ширину скроллбара — `.search-panel__inner`, центрированный внутри панели через `justify-content:center`+`max-width:678px`, пересчитывает свой центр относительно то одной, то другой ширины родителя — отсюда видимый скачок.

Первая попытка фикса — `padding-right: var(--scrollbar-width)` (используя ту же точно измеренную переменную, что уже завели для catalog-menu) — не сработала: `padding-right` просто ДОБАВЛЯЕТ резерв поверх того места, которое и так откусывает реальный скроллбар при своём появлении, вместо того чтобы его ЗАМЕНИТЬ — сдвиг никуда не делся, просто переехал вместе со всей панелью. Правильный инструмент для именно этой задачи — `scrollbar-gutter: stable`: резервирует место заранее, и когда скроллбар реально появляется, он использует уже отведённую полосу, а не откусывает новую — content-box остаётся ОДНОЙ и той же ширины всегда, скролл есть или нет. Добавлен `scrollbar-gutter: stable` на `.search-overlay`. Цена — небольшой постоянный отступ (~15px) с правого края панели даже когда скролл не нужен (тот самый «побочный эффект», который раньше уже убирали по просьбе «белый фон должен быть на всю ширину») — но раз сам скачок контента более заметная и неприятная проблема, чем небольшой всегда-одинаковый отступ, выбор сделан в пользу стабильности.

Проверено через CDP: `.search-panel__inner` `getBoundingClientRect().left/right` идентичны (606/1284) и в пустом состоянии (без скролла), и с 20 результатами (скролл активен) — раньше было 606→598.5 (сдвиг на 7.5px, ровно половина ширины скроллбара). Консоль чистая на 393/834/1920.

**Заказчик прислал ещё один скриншот: справа виден ДВОЙНОЙ отступ** — сам скроллбар, а за ним ещё одна светлая полоса до истинного края экрана («скролл прижался справа [к панели], но не к экрану»). Разобрался глубже: `html{scrollbar-gutter:stable}` (см. `_header.scss`, добавлен намного раньше для другой задачи — чтобы `body{position:fixed}` при блокировке скролла не дёргал шапку/контент вправо на ширину скроллбара) уменьшает ЭФФЕКТИВНЫЙ вьюпорт для **любого** `position:fixed`-элемента на сайте, не только для `body`. Проверено через CDP экспериментально: даже `width:100vw` у `.search-overlay` (по спецификации `vw`-юниты обычно ИГНОРИРУЮТ скроллбары и всегда равны полной ширине экрана — это классический источник нежелательного горизонтального скролла на других сайтах) в этом браузере вернул не `1920`, а `1905` — html-гаттер "просачивается" в расчёт initial containing block для fixed-позиционных потомков, `right:0`/`left:0` у `.search-overlay` читает ту же урезанную величину. Из-за этого сам оверлей был примерно на 15px уже истинного экрана — и поверх этого свой `scrollbar-gutter:stable` у `.search-overlay` (добавленный чуть раньше для фикса сдвига) резервировал ЕЩЁ 15px под собственный скроллбар — отсюда видимая двойная полоса заказчика на скриншоте.

Убирать `html`-гаттер нельзя (протестировано умозрительно и через рассуждение о containing block — без него `body` при блокировке скролла лишился бы своей стабильной ширины, вернулась бы исходная проблема с прыжком шапки). Вместо этого компенсировал явной шириной у самого оверлея: `width: calc(100vw + var(--scrollbar-width, 15px))` — раз `100vw` в этом браузере уже урезан ровно на величину html-гаттера, а `--scrollbar-width` (та же JS-измеренная переменная, что и в catalog-menu) даёт точное значение этой самой величины, их сумма возвращает истинную полную ширину экрана. `.catalog-menu` использует тот же `position:fixed;right:0` паттерн и теоретически подвержен той же усадке — но там это не создавало видимой проблемы (тёмный полупрозрачный фон без чёткой кромки, сайдбар/панель прижаты к ЛЕВОМУ краю, лишние 15px просто остаются неиспользуемым фоном справа) — оставлен как есть, трогать нерабочий код не стал.

Проверено через CDP: `.search-overlay` `getBoundingClientRect()` теперь `{left:0, right:1920, width:1920}` — точно вьюпорт, что до открытия поиска, что после, что с длинным списком результатов; `.search-overlay.clientWidth` (1905) корректно исключает РЕАЛЬНЫЙ скроллбар (когда он есть, на 20 результатах) — то есть теперь ровно один резерв, а не два; `.search-panel` тоже 1905, флаш к скроллбару без зазора. Позиция центрированного контента (`innerLeft/Right`) идентична в пустом и заполненном состоянии — двойной проверкой на два разных прогона. Полный прогон консоли на 393/834/1920 — чисто.

**Формула `100vw + --scrollbar-width` сломала скролл на реальном устройстве заказчика («теперь вообще нет скролла визуально»).** Формула исходила из конкретно НАБЛЮДАЕМОГО в headless Chrome через CDP поведения (`100vw` там оказался урезан ровно на величину html-гаттера) — это Chrome-специфичная (возможно, даже version-специфичная) деталь реализации, не гарантия спецификации. В браузере заказчика `100vw`, судя по всему, НЕ был урезан (ведёт себя как и задокументировано в спеке — игнорирует скроллбары) — добавление `--scrollbar-width` поверх уже-полного значения ПЕРЕкомпенсировало, оверлей стал шире истинного экрана, и сам скроллбар (рисуется у правого края теперь уже нереального, а виртуально-расширенного элемента) физически уехал за пределы видимой области — отсюда «скролла визуально нет» (по факту он есть, просто невидим, за краем экрана).

Заменил гадание формулой на прямое измерение: новая мини-IIFE в начале `main.js` создаёт временный `position:fixed;left:0;right:0` пробник, сравнивает его `offsetWidth` с `window.innerWidth` — разница (`--fixed-width-deficit`) это ТОЧНО то же самое, что применяется к `.search-overlay` в реальности прямо сейчас, в конкретном браузере пользователя, а не предположение о его поведении. В браузерах, где бага нет (html-гаттер не просачивается в fixed-элементы), `--fixed-width-deficit` измерится как `0px`, и `width: calc(100% + 0px)` не меняет естественное поведение оверлея вообще. `.search-overlay` теперь `right:0` (вернул) + `width: calc(100% + var(--fixed-width-deficit, 0px))` вместо прежней `100vw`-формулы.

Проверено через CDP (headless Chrome, где баг воспроизводится): результат идентичен предыдущему фиксу — `.search-overlay` `{width:1920}`, сдвига нет, скролл с 20 результатами работает. Логика теперь самонастраивающаяся, а не завязана на конкретно увиденное в одном браузере поведение — должна корректно работать и там, где бага нет вообще. Консоль чистая на 393/834/1920.

**Даже измерение через пробник не спасло — на реальном устройстве скролл всё равно пропал.** После второй неудачи решил не наращивать компенсации поверх компенсаций, а убрать первопричину. Первопричина — `html{overflow-y:auto; scrollbar-gutter:stable}` (`_header.scss`), заведённый ещё в начале работы над поиском ради одной узкой задачи (чтобы `body{position:fixed}` при блокировке скролла не дёргал шапку/контент на ширину скроллбара вбок). Побочный эффект — это "просачивалось" в расчёт containing block для **любого** `position:fixed`-элемента сайта, по-разному в разных браузерах, и три попытки подряд скомпенсировать именно в `.search-overlay` (формулой через `100vw`, затем измерением пробником) либо не помогали, либо портили другое.

**Убрал `html`-гаттер полностью, решил исходную задачу точечно.** `_header.scss`: `html` больше не трогает `overflow-y`/`scrollbar-gutter`, остался только `scroll-padding-top` (для якорей, не связано). Взамен — `lockPageScroll()` в `main.js` теперь сам компенсирует ширину НАПРЯМУЮ на `body`: перед блокировкой проверяет, был ли у страницы реальный скроллбар (`window.innerWidth > document.documentElement.clientWidth`), и если да — добавляет `body.style.paddingRight = <измеренная scrollbarWidth>px` на время блокировки (снимается в `unlockPageScroll`). Это классический, давно проверенный в реальном мире приём именно для body-lock (используется в Bootstrap-модалках и т.п.) — компенсация точечная, никакого влияния на другие `position:fixed`-элементы сайта. Заодно убрал мёртвый код — пробник `--fixed-width-deficit` и `width:calc(...)` у `.search-overlay` (`right:0`/`left:0` без всяких вычислений теперь работают корректно сами по себе, раз html их больше не портит).

Проверено через CDP: `.search-overlay` в ЗАБЛОКИРОВАННОМ (открытом) состоянии — `{width:1920}`, точно вьюпорт, и в пустом состоянии, и с 20 результатами (без сдвига между ними); `overlayClientWidth` (1905) — ровно ОДИН резерв (свой `scrollbar-gutter` у `.search-overlay`, не два, как раньше при конфликте с html); `hasScroll:true`, скриншот подтверждает — скроллбар на месте, прижат к правому краю экрана, без второй полосы. `lockPageScroll` подтверждённо ставит `body.style.paddingRight:"15px"` при реальном скроллбаре. Каталог-меню (тоже использует общий `lockPageScroll`) по-прежнему блокирует/восстанавливает скролл страницы корректно (`scrollY` 813→заблокировано→813). Полный прогон консоли на 393/834/1920 — чисто.

## Гамбургер-меню (Hamburger Menu)

Файлы: `scss/components/_hamburger-menu.scss`, markup в `index.html` (блок `#hamburger-menu`, в самом конце body), логика — отдельная IIFE в конце `js/main.js`. Мобильный/планшетный аналог Catalog Menu (Figma 75:14223 tablet-закрыто, 75:15671 mobile-закрыто, 75:15948/75:15950 — открытый второй уровень), по прямой просьбе заказчика «оно очень похоже на каталог выпадающий сайдбар — возьми из него основное». Открывается кликом по бургер-иконке в шапке (`#hamburger-trigger`, уже скрытой от `xl` — `d-xl-none`, часть исходной вёрстки).

**Список категорий переиспользует классы `.catalog-menu__group*`/`.catalog-menu__subitem` 1-в-1** — тот же аккордеон, те же `data-panel`/`data-count`, тот же JS-паттерн (наведение/клик подсвечивает и открывает панель), просто внутри `#hamburger-menu` вместо `#catalog-menu` — список категорий в Figma для гамбургера пиксель-в-пиксель совпадает с десктопным сайдбаром. Уникальны только: шапка дровера с лого (`.hamburger-menu__head`, `--header-logo` переопределён локально — этот блок живёт не внутри `.header`, откуда переменная обычно наследуется), пункты «Компания/База знаний/Контакты», блок контактов + кнопка «Заказать звонок» (`.hamburger-menu__contact*`), и второй уровень.

**Второй уровень — отдельный полноэкранный слой, а не панель рядом (по явной правке заказчика: «второй уровень здесь открывается отдельным слоем а не рядом»).** В отличие от десктопа, где сайдбар и контент-панель показаны одновременно бок о бок, здесь `.hamburger-menu__detail` при `is-level2` занимает всё доступное пространство оверлея (`flex:1`), а `.hamburger-menu__drawer` (первый уровень) в этот момент скрыт (`display:none`) — визуально это «переход на следующий экран», с кнопкой «Назад» (`.hamburger-menu__back`) для возврата. Карточки товаров и сетка — новые классы `.hamburger-menu__grid`/`.hamburger-menu__card`, а не переиспользованные `.catalog-menu__card`: у десктопа сетка ручная, фиксированной ширины 176px по 4 в ряд (JS сам режет на строки), здесь нужна именно резиновая раскладка под две реальные ширины экрана — 2 колонки на мобилке, 3 — с `md` (планшет), обычный CSS Grid сам переносит карточки без ручного деления на ряды.

Демо-данные те же, что у catalog-menu (тот же пул `PRODUCTS` в `js/main.js`, своя копия внутри IIFE гамбургера — рендер-код разный из-за грида, а не построчной раскладки) — реальные карточки есть только для «Ультразвуковой контроль», остальные пункты переиспользуют тот же пул с разным `data-count` для наглядности переключения (та же имитация, что и в catalog-menu, см. выше).

Взаимное исключение: открытие поиска закрывает гамбургер-меню (и наоборот, десктопный catalog-menu тоже закрывается гамбургером — оба используют общий `lockPageScroll()`/`unlockPageScroll()`).

**Баг сразу после первой сборки: оверлей не затемнял шапку, хотя по хит-тестингу (`elementFromPoint`) был поверх неё.** Потратил много времени на неверную гипотезу — что `body{position:fixed}` (общий `lockPageScroll()`) ломает stacking context для вложенных `position:fixed` элементов, проверял z-index/isolation/compositing-хинты (`translateZ(0)`, `will-change`, `isolation:isolate`, максимальный z-index) через CDP — ни один не помог. Настоящая причина оказалась гораздо проще: у catalog-menu `openMenu()`/`closeMenu()` переключают класс `.header--menu-open` на `.header` (принудительно красит шапку в сплошной белый — см. правки catalog-menu выше, пункт 4 «шапка всегда белая»), а у гамбургер-меню эту строчку я просто забыл добавить при первой сборке — шапка оставалась в дефолтном прозрачном `.header--overlay` виде, и полупрозрачный тёмный фон оверлея (`--color-surface-popup`, тот же токен, что у catalog-menu/search) реально красился под ней технически корректно, просто через прозрачную шапку это не было заметно так, как ожидалось. Добавлено `header.classList.add/remove('header--menu-open')` в `openMenu()`/`closeMenu()` гамбургера — по образцу catalog-menu. Заодно у поиска (`open()`, который принудительно закрывает и catalog-menu, и гамбургер при открытии) добавлен `header.classList.remove('header--menu-open')` — раньше принудительное закрытие соседних меню не снимало этот класс, шапка могла «залипнуть» белой при переходе catalog-menu/гамбургер → поиск.

**Баг с прыжком шапки при блокировке скролла — воспроизводится только после прокрутки, найден и исправлен.** Заказчик заметил: если открыть гамбургер-меню/каталог-сайдбар/поиск ровно в самом верху страницы (scrollY=0), прыжка нет — а если предварительно прокрутить страницу вниз и открыть любое из этих меню оттуда, шапка резко становится шире всего остального контента. Sticky-шапка выше) имеет СВОЙ containing block — вьюпорт целиком, а не `body`. Общая компенсация ширины скроллбара в `lockPageScroll()` (`body.style.paddingRight`) действует только на элементы, чья ширина зависит от `body`-контейнера (весь обычный поток документа, включая саму шапку, ПОКА она `position:absolute` внутри `.hero`, т.е. до прокрутки) — но `position:fixed`-элемент, как `.header--stuck`, полностью выходит из этой цепочки и продолжает растягиваться на полную ширину вьюпорта (`right:0` от `.header--overlay`, унаследованный и в состоянии `--stuck`), независимо от паддинга `body`. Отсюда рассинхронизация именно в прокрученном состоянии: шапка (не компенсирована, полные 1920px) против остального контента (компенсирован, 1905px). Пока `.header--stuck` не применилась (самый верх страницы), шапка — обычный `position:absolute` элемент внутри `.hero`, часть общего потока, компенсируется вместе со всем остальным — оттуда и «прыжка нет» именно наверху. Фикс — `lockPageScroll()`/`unlockPageScroll()` (общие для поиска/catalog-menu/гамбургера) теперь дополнительно проверяют `.header--stuck` при блокировке: если она сейчас `position:fixed` И у страницы реальный скроллбар, применяют тот же самый отступ напрямую через `header.style.right = scrollbarWidth + 'px'`, снимают его при разблокировке. Скролл-слушатель `.header--stuck` и так уже не переключает класс, пока `body.style.position === 'fixed'` (более раннняя правка, см. запись про Search выше) — то есть состояние «прилипшая/не прилипшая» гарантированно не меняется в течение блокировки, значение `right` можно спокойно выставить один раз при открытии. Проверено через CDP на 1920/834: на scrollY=800 (`.header--stuck` активна) ширина шапки (`getBoundingClientRect().width`) теперь идентична ширине `.hero` (1905/819) и ДО, и ПОСЛЕ открытия любого из трёх оверлеев (раньше расходилась на 15px после открытия) — проверено для catalog-menu, гамбургер-меню и поиска по отдельности; `header.style.right` корректно ставится `"15px"` при открытии и снимается (`""`) при закрытии. Полный регрессионный прогон (открытие/уровень2/назад/закрытие) на 393/834 — 0 исключений.

**Реальный баг на узких телефонах: карточка дровера не сужалась вслед за внешним скролл-слоем, крестик закрытия мог оказаться обрезан или вообще уехать за экран.** Заказчик прислал наблюдение: на телефоне отступ от крестика до края экрана на первом уровне меню отличается от второго — при переходе между уровнями крестик «прыгает». Причина глубже, чем просто разные отступы: у `.hamburger-menu__drawer` (внешний скролл-слой) уже был `max-width:100%`, а у `.hamburger-menu__drawer-inner` (видимая карточка) — нет, она держала жёсткие `width:393px` без ограничения сверху. На экранах уже 393px (реальные телефоны — 320/360/375px, не только гипотетические) внешний слой корректно сжимался до ширины экрана, а внутренняя карточка — нет, оставалась 393px и переполняла внешний контейнер; `overflow-x:hidden` молча обрезал лишнее справа. Второй уровень (`.hamburger-menu__detail`) устроен иначе — `flex:1`, честно занимает всю реальную ширину оверлея, без фикс-ширины и без обрезания. Отсюда: на узких экранах крестик первого уровня стоял у правого края НЕсуществующей 393px-широкой (и местами обрезанной) карточки, а крестик второго уровня — у истинного края экрана; на 320px разница доходила до того, что крестик первого уровня полностью уезжал за пределы видимой области (`right:377` при ширине экрана `320`). Фикс — `.hamburger-menu__drawer-inner{max-width:100%}`. Проверено через CDP на 375/360/320: `drawerInnerWidth` теперь точно равен ширине экрана на всех трёх (было неизменно `393` независимо от вьюпорта); `getBoundingClientRect()` крестика полностью совпадает между первым и вторым уровнем на каждом из трёх вьюпортов (было расхождение вплоть до 73px на 320px).

**Мобильный паддинг шапок дровера/деталей уменьшен по просьбе заказчика.** `.hamburger-menu__head` и `.hamburger-menu__detail-head` получили `padding-top`/`padding-bottom: 12px` (было `16px`, единое для всех брейкпоинтов) под `media-breakpoint-down(md)` — левый/правый паддинг не тронут, планшет/десктоп не затронуты (там по-прежнему `16px` со всех сторон). ## Как мы пишем код

- **Сначала утилиты Bootstrap** (`d-flex`, `gap-3`, `px-3`, `d-none d-md-block`), а в SCSS только то, что утилитами не покрыть.
- **Один компонент — один файл** в `scss/components/_имя.scss`, подключается в `main.scss` после Bootstrap. Классы в БЭМ: `header__logo`, `card--active`.
- **Цвета и размеры шрифтов только из переменных** (`var(--color-…)`, `var(--h2-size)`), не hex и не пиксели.
- **Комментарии объясняют «почему»**, а не «что»: например, зачем перебит стиль Bootstrap. Так сделано в Domarti.
- **Скрипты** в `js/main.js`: по одной самовызывающейся функции на компонент, без jQuery, инициализация по классам и data-атрибутам.
- HTML: каждая страница отдельным файлом в корне; шапка и футер повторяются в каждом (шаблонизатора нет).
- Кнопки без класса `.btn` (иконочные) наследуют шрифт и `cursor: pointer` из `_tokens.scss`.

## Что решено, а что нет

Решено при создании каркаса:

- Подключён только CSS Bootstrap. JS Bootstrap (выпадающие меню, модалки) не подключён, добавим, если понадобится.
- Swiper (слайдеры) не установлен, в Domarti он был, поставим, когда дойдём до слайдеров.
- Тёмная тема Bootstrap выключена (`$enable-dark-mode: false`), сайт только светлый.
- Репозиторий: https://github.com/artsman01/stc (ветка `main`). Автодеплой (в Domarti это GitHub Actions по FTP на Timeweb) не настраивался; `css/style.css` закоммичен, поэтому сайт можно раздавать и без сборки.

Ждёт решения:

- Максимальная ширина контента на экранах шире 1600px (в макете такого нет).
- Фильтрация каталога по табам («Все» / «Неразрушающий контроль» / …) — сейчас чисто визуальная, JS не подключён.
- Реальные ссылки карточек и кнопки «Перейти в каталог» — сейчас все ведут на `catalog.html`, которого ещё нет.
- Форма в CTA никуда не отправляется (нет `action`, нет бэкенда), ссылки на политику обработки данных ведут на `#`.
- Фото hero на tablet (768px): берётся вертикальная `hero-compact.jpg`, и прибор на ней крупнее, чем в макете tablet. Для точного совпадения нужна отдельная картинка (тогда добавится ещё один `<source>` в `<picture>`). Оба jpg весят 0.9 и 0.6 МБ, при желании можно сжать или перевести в WebP.
- Ховер шапки: в макете нарисован только desktop. Tablet и mobile получают такое же поведение. Цвет ховера ссылок (сейчас `brand-primary`) и кнопок в белой шапке (сейчас `border-default`) в макете не заданы, взяты из палитры.

## Для Claude: как достать данные из Figma

Figma Dev Mode MCP-сервер работает локально на `http://127.0.0.1:3845/mcp` (нужно запущенное приложение Figma). Если инструментов Figma в сессии нет, к серверу можно обратиться напрямую по HTTP (JSON-RPC: `initialize`, затем заголовок `mcp-session-id`). Полезные методы: `get_variable_defs` (цвета и типографика), `get_metadata` (структура), `get_design_context` (макет + ссылки на SVG-ассеты), `get_screenshot`. Векторные иконки Figma отдаёт кусками, полный SVG приходится собирать по отступам и зеркалированию из `get_design_context`. Node-id нужных фреймов указаны выше.

Нюансы, на которые уже наступали:

- `get_design_context` на узле-экземпляре (например `36:2137`) возвращает код главного компонента, то есть desktop-вариант. Реальные tablet и mobile получаются, если запросить весь фрейм страницы (`36:2136`, `36:3007`) и найти в коде блок `data-name="Hero"`.
- Вложенные id вида `I36:2137;36:2761` инструмент не принимает.
- Скачанные из Figma растровые картинки приходят шириной 1024px.
- Headless Chrome не уменьшает окно меньше ~500px, поэтому мобильную раскладку проверять через `<iframe width="393">`, а не `--window-size=393`.
